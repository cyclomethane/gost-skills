# SKILL: ГОСТ Р 7.0.108-2022 — ссылки на сетевые электронные документы

Версия SKILL: 2026-09-16  
Нормативная основа: **ГОСТ Р 7.0.108-2022 «СИБИД. Библиографические ссылки на электронные документы, размещённые в информационно-телекоммуникационных сетях. Общие требования к составлению и оформлению»**. Стандарт действует с 01.06.2022.

Официальная карточка: https://protect.gost.ru/gost/details/df775619-cc9b-4cea-af6e-83e31a0aab9e


Приоритет требований, статусы правил MUST/SHOULD/MAY/LOCAL, общая процедура
аудита и формат отчёта — `SKILL.md`. Вёрстка — `layout-core.md`; обязательные
элементы и объём — `mandatory-core.md`.

## 1. Назначение

Стандарт применяется к библиографическим ссылкам на электронные документы сетевого распространения: сайты, страницы сайтов, сетевые статьи, электронные журналы, PDF, базы данных, репозитории, официальные документы, стандарты в сети и другие электронные документы.

Он дополняет общий ГОСТ Р 7.0.5-2008 и использует базовые правила библиографического описания ГОСТ Р 7.0.100-2018.

## 2. Объект ссылки

Ссылка составляется на конкретный электронный документ или его часть. Для изменяемых ресурсов критично фиксировать именно ту версию, которая доступна по указанному URL.

## 3. Полная и краткая ссылка

Полная ссылка даёт развёрнутую идентификацию объекта. Краткая ссылка используется, когда часть сведений уже присутствует в тексте или затекстовом перечне. В обоих случаях URL должен вести к объекту, который реально использовался.

## 4. Заголовок и библиографическое описание

Ссылка на сетевой документ строится с использованием:
- заголовка библиографической записи;
- библиографического описания;
- сетевых реквизитов.

Для имен авторов и структуры записи применять действующие библиографические стандарты.

## 5. Заглавие

Основное заглавие брать с титульной страницы/заголовка электронного документа. Для PDF использовать заглавие самого документа; имя файла служит только техническим ориентиром.

## 6. Сведения об ответственности

Указывать автора, организацию, редакцию или иной ответственный субъект, если это помогает идентифицировать документ.

## 7. Сетевой адрес

Для сетевой ссылки приводить:
- метку `URL:`;
- полный адрес с протоколом (`https://`, `http://`, `ftp://` при соответствующем ресурсе);
- дату обращения в формате `ДД.ММ.ГГГГ`, когда она предусмотрена стандартом.

Рабочая форма:
`URL: https://example.org/document (дата обращения: 16.09.2026).`

## 8. Дата обращения

Дата обращения фиксирует момент, когда автор реально видел ресурс. Её следует обновлять только после повторной фактической проверки ресурса.

Для автоматически генерируемой библиографии хранить дату обращения как отдельное поле.

## 9. DOI

Для научной статьи с DOI устойчивый идентификатор предпочтителен для поиска. DOI следует проверять через официальный резолвер и воспроизводить без искажений. Локальный журнал может требовать форму `https://doi.org/...`.

## 10. Дата публикации и обновления

Если ресурс содержит дату публикации, версию или дату обновления, включать её в запись по правилам стандарта и локального формата. Для динамических страниц дата обращения остаётся отдельным реквизитом.

## 11. Режим доступа

Режим доступа указывается, когда ресурс имеет специальные условия использования, например подписку, договорный доступ или локальную сеть.

## 12. Сайт целиком

При ссылке на сайт в целом идентифицировать организацию/проект и официальный характер сайта при наличии такого статуса.

Типовая схема:
`Название организации/сайта : характеристика ресурса. URL: ... (дата обращения: ...).`

## 13. Отдельная веб-страница

Для отдельной страницы фиксировать:
- автора/организацию;
- заглавие страницы;
- сайт;
- дату публикации/обновления при наличии;
- URL;
- дату обращения.

Ссылка должна вести на страницу, где находится цитируемая информация.

## 14. PDF в сети

Если используется PDF:
- описывать содержательный документ;
- указать автора/организацию и заглавие;
- зафиксировать год/версию;
- использовать прямой URL к документу либо устойчивую карточку;
- указать дату обращения.

## 15. Научная статья онлайн

При наличии нормальных журнальных метаданных запись должна сохранять библиографию статьи: авторов, заглавие, журнал, год, том, номер, страницы/номер статьи и DOI. URL страницы издателя служит дополнительным средством доступа.

## 16. Репозиторий

Для материала в репозитории указать:
- автора;
- заглавие;
- тип материала при необходимости;
- репозиторий;
- дату;
- устойчивый идентификатор/URL;
- дату обращения.

## 17. Набор данных

Для набора данных желательно фиксировать:
- автора/организацию;
- точное название;
- версию;
- год;
- платформу/репозиторий;
- DOI/URL;
- дату обращения;
- лицензию, если её наличие важно для воспроизводимости исследования.

## 18. Программное обеспечение и GitHub

Когда ссылка ведёт на программу или репозиторий:
- название проекта;
- автор/организация;
- версия, релиз или commit/tag для воспроизводимости;
- платформа;
- URL;
- дата обращения.

Для научного эксперимента предпочтителен фиксированный release/tag/commit.

## 19. Электронный стандарт

При ссылке на стандарт в сети сначала идентифицировать сам стандарт, затем его электронное местонахождение. Статус проверять по Росстандарту. Для нормативных утверждений использовать официальную карточку как первичный источник статуса.

## 20. Нормативный правовой акт в сети

Предпочтительны официальные правовые системы и официальные сайты органов власти. Запись должна идентифицировать конкретный акт, редакцию/дату и сетевой источник.

## 21. Страница без автора

Использовать заглавие документа и организацию/сайт как идентифицирующие элементы. Авторство по домену или предположению не добавлять.

## 22. Страница без даты

Сохранять проверяемые элементы и дату обращения. Фиктивную дату публикации не выводить из даты файла, поискового сниппета или текущей даты.

## 23. Изменяемый документ

Для wiki, документации, live-dashboard и иных изменяемых страниц использовать максимально устойчивую версию: permalink, release, commit, архивную копию или версионную страницу, если она доступна и соответствует реально использованному материалу.

## 24. Проверка URL

Перед сдачей:
1. выполнить HTTP-проверку;
2. убедиться, что открывается нужный документ;
3. проверить редиректы;
4. исключить временные токены авторизации;
5. исключить поисковые URL;
6. использовать HTTPS, когда официальный ресурс поддерживает его.

## 25. Университетская стратегия

Для диссертации и ВКР хранить сетевые источники в библиографическом менеджере с отдельными полями:
- title;
- author/organization;
- publication date;
- website/publisher;
- DOI;
- URL;
- accessed date;
- version;
- notes/access mode.

## 26. Типичные дефекты

- URL ведёт на поисковую выдачу;
- URL ведёт на главную страницу вместо документа;
- пропущена дата обращения для изменяемого ресурса;
- дата обращения выдумана;
- DOI оформлен как обычный URL с лишними параметрами;
- ссылка содержит session-id/token;
- заглавие взято из имени файла;
- отсутствует организация-источник;
- репозиторий указан без версии используемого кода;
- один и тот же ресурс оформлен несколькими способами.

## 27. Машинный чек-лист

- [ ] URL открывается.
- [ ] URL ведёт к нужному объекту.
- [ ] Протокол указан.
- [ ] Дата обращения присутствует там, где требуется.
- [ ] Заглавие совпадает с документом.
- [ ] Автор/организация подтверждены источником.
- [ ] Дата публикации/версия подтверждены.
- [ ] DOI проверен.
- [ ] Режим доступа описан при специальных условиях.
- [ ] Для кода/данных указана воспроизводимая версия при наличии.
- [ ] Запись согласована с ГОСТ Р 7.0.100-2018.
- [ ] Отсылка в тексте согласована с ГОСТ Р 7.0.5-2008.
